1. Why this change

Legacy jobs authorize the card with capture_method: manual. Stripe holds die ~7 days. The violin job hit that wall; the keyboard job is the same shape. Charge-at-post via Stripe Checkout (auto-capture) removes the hold timer. Money sits on the platform until award → Connect transfer (or admin manual PayPal/Wise).

You already agreed charge-at-post is the right product move if refunds, claim locks, cron sweeps, price ceiling, and idempotency ride along. This plan is that “same change,” not Checkout bolted on alone.

Live constraint right now. Aaron submitted a keyboard take; Luke reviewed — usable. Bryon still needs to End gig & pay on production (old path) before the hold expires. Deploying Checkout before that award is an unnecessary risk on that one job.

2. New job money lifecycle

POST /api/jobs → create Job status = PENDING_PAYMENT + Payment (pending PI placeholder) → Stripe Checkout Session (mode=payment, idempotencyKey job_checkout_{jobId}) → producer pays on Stripe-hosted page checkout.session.completed (webhook) OR GET confirm-checkout fallback → Payment.status = captured, store real PI id (@unique) → Job.status = OPEN (+ invite / new-job emails) Producer: End gig & pay / cron finalize → claim OPEN → AWARDING (updateMany count===1; resume after 30s if stuck) → if PI requires_capture: capture (legacy holds) else already succeeded → transfers.create (idempotencyKey job_transfer_{jobId}) OR pending_manual_payout → Job = AWARDED Producer cancel / unpaid abandon / cron no-winner past grace → claim → CANCELLING → requires_capture → PI cancel → succeeded → refunds.create (idempotencyKey job_refund_{jobId}) → unpaid Checkout → sessions.expire → Job = CANCELLED checkout.session.expired → abandon unpaid PENDING_PAYMENT draft

Legacy keyboard job stays OPEN + authorized PI until Bryon finalizes. New statuses are additive; old code paths still capture when requires_capture.
